# RBEL-CRM — Financial Advisor Client Management & Analytics

A CRM for a financial advisor: clients, policies, **policy owners and policy insureds (always kept separate)**, beneficiaries, coverage documents, appointments, reminders, goals, email templates, audit trail and analytics.

| Layer | Stack |
|---|---|
| Frontend | React 19 · TypeScript · Tailwind CSS v4 · shadcn/ui (Radix) · Recharts · TanStack Query · React Router · react-hook-form + zod |
| Backend | Laravel 13 · PHP 8.3 · Sanctum (SPA cookie auth) · Form Requests · API Resources · Laravel Mail · Laravel Storage |
| Database | MySQL 8+ (developed on MySQL 9.1) · views · CTEs · window functions · stored procedures · generated columns · CHECK constraints |

The React app is built by Vite inside the Laravel project and served from the same origin, so authentication uses Sanctum's session cookie with CSRF protection instead of bearer tokens stored in the browser.

> **Demo version.** This repository contains only code and **synthetic demo data** generated by the seeders. It includes no real clients, policies or documents.

## 1. Quick start

Prerequisites: PHP 8.3+, Composer, Node 20+, and a **MySQL 8+** server. MariaDB and XAMPP's bundled MySQL 5.x are not supported: the app relies on MySQL-only features such as `EXPLAIN ANALYZE`, window functions inside views, and real `JSON` columns.

```bash
composer install
npm install
cp .env.example .env         # then edit DB_* for your MySQL server
php artisan key:generate

# create the databases (app + tests)
mysql -uroot -e "CREATE DATABASE rbel_crm_demo CHARACTER SET utf8mb4; CREATE DATABASE rbel_crm_demo_test CHARACTER SET utf8mb4;"

php artisan migrate --seed   # schema, views, procedures + synthetic demo data
npm run build
php artisan serve --host=localhost --port=8020
```

Open **http://localhost:8020**. On Windows you can double-click `start-crm.bat` instead.

To reset the demo data at any time: `php artisan migrate:fresh --seed`.

To put the demo online, see **[docs/DEPLOY-VERCEL.md](docs/DEPLOY-VERCEL.md)** (Vercel + a free Aiven MySQL database).

For frontend hot-reload, run `npm run dev` alongside `php artisan serve`.

### Local environment

- MySQL 9.1 on port **3306** (for example WAMP's MySQL), databases `rbel_crm_demo` and `rbel_crm_demo_test` (`.env`, `phpunit.xml`)
- App on port **8020**
- `APP_TIMEZONE=Asia/Manila` and `DB_TIMEZONE=+08:00`. These keep PHP's `today()` and MySQL's `CURDATE()` on the same date, which the dashboard's "due today" and age calculations depend on.
- `.htaccess` denies all Apache access to the project folder, so if it sits in a web root (such as `wamp64/www`), Apache never serves `.env`, `storage/` or the source code. The app itself is served by `php artisan serve`.

### Sending email

Emails go out through one shared Gmail account. The recipient sees the signed-in user as the sender (**"Maria Santos via RBEL-CRM"**), and replies go to that user's own email (their Profile email), via Reply-To. The From address has to be the Gmail account itself, because Gmail rejects mail that claims to come from someone else.

1. On the Google account used for sending: turn on **2-Step Verification**, then create an **App Password** (Google Account > Security > App passwords).
2. Sign in as an admin, open **Profile**, and go to **Email sending**. Click **Gmail** to fill in the server, enter the Gmail address and the App Password, switch sending **on**, and **Save**.
3. Click **Send test** to check delivery.

These settings are stored in the database, and the password is encrypted with `APP_KEY`. They override the `MAIL_*` values in `.env`, which only apply until the settings are first saved. If `APP_KEY` ever changes, re-enter the password in Profile. `php artisan crm:mail-test you@example.com` also checks the active settings from the command line.

### Automations (birthday greetings and payment reminders)

**Automations** (admin menu) sends two daily emails:
- **Birthday greetings** go to every client and lead whose birthday is today. Feb 29 birthdays are greeted on Feb 28 in non-leap years.
- **Payment reminders** go to the **Policy Owner** of every active policy whose premium is due today (the same list as the dashboard's "Due today"). Templates can use `{{premium_due}}` and `{{due_date}}`.

Each automation has an on/off switch, a template, a daily send time and a "send as" user. Both start **off**. The page lists today's recipients before anything is sent, and **Run now** sends immediately. A person or policy gets an automated email at most once a day. A failed send can be retried later the same day.

Turned-on automations send **by themselves** once their daily send time passes. The scheduler checks every minute. It runs through the Windows scheduled task **"RBEL-CRM Demo Scheduler"**, which starts again after a restart and runs hidden for the logged-in user:
- Install: `powershell -ExecutionPolicy Bypass -File install-scheduler.ps1`
- Remove: the same command with `-Uninstall`. Output goes to `storage/logs/scheduler.log`.
- Manual alternative: double-click `start-scheduler.bat` and keep the window open.
- The Automations page shows a green "Automatic sending is running" line while the scheduler is checking in. It turns amber when it isn't.
- To check without sending: `php artisan crm:automations --dry-run` lists today's recipients.
- MySQL must be running for automations to send.

While `MAIL_MAILER=log`, nothing is delivered. The send dialog says delivery isn't set up, and any attempt is logged as **failed** instead of "sent". Gmail allows about 500 emails a day per account.

## 2. The core business rule: Owner ≠ Insured

`policies` has **two separate foreign keys to `clients`**:

- `policy_owner_id`: the client who owns and pays for the policy (must be flagged `is_policy_owner`)
- `policy_insured_id`: the client whose life or health is covered

They may point to the same client (self-insured) or to different clients (for example, a parent owns a policy insuring a child). There is no generic single "client of the policy" column anywhere; leads and beneficiaries live in their own tables (`leads`, `beneficiaries`).

| Where | How the separation is enforced |
|---|---|
| Schema | two FKs, two composite indexes `(policy_owner_id, issued_date)` and `(policy_insured_id, issued_date)` |
| Policy search | owner and insured joined under separate aliases (`owner`, `insured`). Separate filters (`policy_owner_id`, `policy_insured_id`), searches (`owner_search`, `insured_search`) and sorts (`policy_owner`, `policy_insured`) |
| UI | separate "Filter by Policy Owner" and "Filter by Policy Insured" pickers. The client page lists "Policies owned" and "Policies insuring X" separately |
| Analytics | every person-based metric takes `role=owner` or `role=insured`. Age uses `owner.birthdate` or `insured.birthdate` accordingly |
| Tests | `tests/Feature/PolicyOwnerInsuredFilterTest.php` plus role assertions in the analytics tests |

The seed data contains about 134 of 357 policies where owner ≠ insured: children, spouses and elderly parents.

## 3. Features

- **Authentication**: login with remember-me, logout, session restore, throttled login (5 failed attempts per email+IP), change password (other sessions are signed out), profile.
- **Dashboard**: KPIs (Total Clients, Pending Policy Delivery, Appointments, Goals, Churn/Inactive), Due Today (premiums due, reminders including overdue, appointments, deliveries pending 7+ days), Birthdays and Policy Anniversaries for any selected month and year, a Jan–Dec sales bar chart by year, and an age-range donut with a **Policy Owner / Policy Insured** switch.
- **Clients**: server-side search, filter (role, status, gender, birth month), sort and pagination. The profile shows owned policies, insured policies, a policy activity timeline (LAG/LEAD) and appointments.
- **Policies**: CRUD with beneficiaries saved in the **same transaction**, every filter from the spec, and URL-persisted table state.
- **Leads**: a separate `leads` table with notes; a lead is converted into a client when they buy.
- **Beneficiaries**: stored as rows in `beneficiaries`, with their own details (never a text list). Supports primary and contingent types, revocable and irrevocable designations, and allocation %. All beneficiaries together must total 100%.
- **Coverage documents**: upload, view, download, replace and delete. PDF/JPG/PNG up to 10 MB, content-sniffed, stored on the private disk under random names, and streamed only through authenticated routes.
- **Appointments, Reminders, Goals**: CRUD, filters, and goal progress capped at 100%.
- **Email templates**: CRUD, duplicate, live preview, placeholders, and send via Laravel Mail. The email log masks recipient addresses and does not store message bodies.
- **Analytics**: monthly and annual APE, YoY, product/status/payment-mode breakdowns, delivery aging, gender and generations (Gen Z, Millennials, …, by birth year) by role, top clients by APE (DENSE_RANK and cumulative share), retention and churn, and per-person sales by role.
- **Audit log**: automatic created/updated/deleted entries for all CRM models (changed fields only, as JSON old/new values), plus login, document, email and settings events. Admin only.

### Churn definition

> A client is **inactive (churned)** when they own **no in-force policy** (status `active`, `cooling_off` or `pending`) and at least one of their policies was **terminated, lapsed or surrendered**. Clients whose policies only matured are **completed**, not churn; prospects are excluded. **Churn rate = inactive ÷ (active + inactive) policy owners.**

The definition lives in one place, `vw_client_policy_overview.client_status`. The API returns the definition text alongside the numbers, and the UI shows it in a tooltip.

```bash

npx tsc --noEmit            # frontend type check
```

Tests use MySQL, not SQLite, because the app depends on views, stored procedures, window functions and generated columns. They cover authentication and rate limiting, client and policy CRUD, **owner vs insured filtering**, beneficiaries, appointments, goals, reminders, dashboard calculations, sales and age analytics, file uploads, email templates (preview escaping, sending, failure logging), audit logging, authorization per role, validation, and SQL-injection-style inputs.

## 6. Security summary

- Sanctum SPA session auth. All CRM routes are behind `auth:sanctum`, and CSRF protection applies to every state-changing request.
- Role gates: `manage` (admin, advisor) for deletes and email sending; `admin` for the audit log and settings.
- Rate limits: login (5 failed attempts per email+IP, 10 requests/min per IP), API (180/min), uploads (20/min), emails (30/min), password change (6/min).
- All input is validated by Form Requests. Queries use parameter binding, sort columns come from whitelists, and `LIKE` wildcards are escaped.
- XSS: React escapes output. Email bodies are rendered as escaped plain text, and subjects are stripped of CR/LF.
- Uploads: MIME is sniffed from content, size is limited, files live on the private disk under random names, and responses send `nosniff`.
- Responses never include password hashes, remember tokens or file-system paths. Email logs mask addresses.
- Security headers on every response: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`.

See `docs/` for the schema, API reference and query plans.
